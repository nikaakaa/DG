# 节奏输入与大世界工厂网络同步技术报告

报告日期：2026-05-12  
范围：`DG` 当前服务端权威移动链路、节奏输入手感、大世界工厂同步策略  
结论级别：技术路线报告，不是已批准的 OpenSpec 需求

## 1. 核心结论

`DG` 更像“大世界工厂 + 服务端权威 + 多人协作”的方向，不适合走全世界 rollback。

节奏输入可以做，重手感也可以做，但推荐路线不是格斗游戏式 rollback，也不是把整个世界按历史帧倒回去重放。更合适的是：

```text
服务端权威大世界
+ 客户端即时反馈
+ 玩家局部预测
+ 服务端最终结算
+ 客户端软校正
+ 小范围冲突裁决
```

大世界工厂里的机器、区块、生产线、库存流转、机关链和多人世界状态，应长期由服务端权威 tick 推进。客户端不能成为规则真相源，也不应该回滚整片世界。

当前最推荐的第一步是：

```text
Beat Input Buffer
```

也就是先把玩家输入从“现在请求移动”升级为“某一拍的最终意图”。这一步只解决输入语义和一拍多输入问题，不引入完整预测，也不引入全局 rollback。

## 2. 当前项目现状

当前服务端移动链路大致是：

```text
C2G_MoveRequestHandler
  -> AuthoritativeInputQueue.EnqueueMove
  -> await input.WaitAsync

AuthoritativeWorldTickRunner.Tick
  -> World.NextTick
  -> InputQueue.DrainMoves
  -> 每个输入转成 WorldAction
  -> RuleExecutionSystem.Tick
  -> SyncSystem.BroadcastDelta
  -> 完成 Move RPC
```

当前关键特征：

- 逻辑 tick 和 `WorldDelta` 广播暂时绑在一起。
- `TickIntervalMs = 200`，逻辑和 delta 广播都是 5Hz。
- 移动 RPC 会等待服务端下一次逻辑 tick 结算后才回包。
- 客户端主要等 RPC response 或 `WorldDelta` 后再应用最终状态。
- `AuthoritativeInputQueue` 是普通队列，同一个实体在一个逻辑 tick 内可以提交多个输入。
- 规则层会仲裁世界冲突，但输入层还没有“每拍最终意图”的模型。

当前有利基础：

- `Shared/DG.GameCore` 已经承载核心世界和规则。
- 服务端和客户端可以共享 `GameWorld`、规则、快照、delta 类型。
- 规则逻辑没有绑死在 Unity MonoBehaviour 上。
- 已经有 `ServerTick`、`WorldAction`、`WorldDelta`、`EntitySnapshot` 等概念。
- 项目约束已经明确：服务端权威 `GameWorld` 是多人同步和规则裁决的真相源。

这些基础支持继续演进到输入缓冲、即时反馈、局部预测和软校正。

## 3. 问题本质

问题不是单纯 tick 频率不够，也不是只要把 tick 改成 20ms 就能解决。

普通服务端权威链路关注：

```text
状态正确
防作弊
所有人最终一致
```

节奏手感还需要：

```text
按键瞬间有反馈
输入贴近本机节奏时间
玩家不能等网络往返才看到反应
音乐和节拍 UI 不能被网络校正拖拽
```

大世界工厂还额外要求：

```text
世界状态可扩展
区块和机器不频繁倒带
服务端仍是最终真相
多人观察到同一份 WorldDelta
客户端表现不能篡改规则结果
```

所以真正的矛盾是：

```text
本地即时手感 vs 服务端权威大世界一致性
```

解决方向不是全局回滚，而是把问题拆开：

- 输入层按节拍收口。
- 表现层立即反馈。
- 玩家局部状态可以短期预测。
- 服务端仍按权威 tick 结算。
- 客户端收到权威结果后平滑确认或校正。

## 4. 为什么不做全世界 rollback

完整 rollback/replay 适合状态规模小、参与对象少、逻辑高度确定、历史窗口短的游戏，比如格斗游戏或小型同步对战。

`DG` 如果走大世界工厂方向，全世界 rollback 会带来明显问题：

- 世界范围大，保存每拍完整快照成本高。
- 工厂机器和机关链可能跨区块、跨大量实体。
- 多人同时操作会让历史输入和世界状态组合变复杂。
- 区块加载、实体生命周期、配置驱动规则都会增加重放成本。
- 已经播放的表现、音效、节拍 UI 和玩家反馈不适合倒回。
- 服务端 Fantasy 世界长期运行，不能为了玩家输入频繁倒带整套状态。

因此本项目不建议把 rollback 作为主路线。

更准确的边界是：

```text
不回滚整个世界
不回滚音乐时间线
不回滚工厂生产主状态
不回滚已确认的服务端权威历史

可以做玩家局部预测
可以做客户端软校正
可以在很小范围内做冲突重算
可以为特殊玩法保留局部快照
```

这里的“小范围”指同一格、同一交互簇、同一短时间窗口内的玩家或机关冲突，不是整个大世界。

## 5. 推荐架构方向

### 5.1 输入表示某一拍的意图

输入不应该只表示“现在按了什么”，而应该表示：

```text
某个实体在某一拍提交了某个最终意图
```

未来输入协议语义可以接近：

```text
clientInputId
entityId
targetBeatTick
direction
clientBeatTimeMs
localJudgeOffsetMs
```

第一阶段可以不立即修改 Outer 协议，让服务端先根据收到输入的时间归属到目标拍。系统内部应先改成：

```text
entityId + beatTick -> final input
```

### 5.2 服务端节拍输入缓冲

服务端新增输入缓冲层：

```text
BeatInputBuffer
  Submit(entityId, direction, receiveTime, clientInputId)
  Drain(beatTick)
```

职责：

- 根据服务器节拍时钟把输入归属到目标拍。
- 同一实体同一拍最多保留一个最终输入。
- 默认最后输入覆盖旧输入。
- 被覆盖输入返回明确状态。
- 当前拍只消费当前拍输入。
- 未来拍输入不能提前消费。

建议状态：

```text
Buffered
Replaced
Consumed
Expired
Rejected
Resolved
```

第一版策略：

```text
同一实体同一拍取最后一次输入
```

理由是节奏窗口内允许玩家修正方向，手感更宽容，也能避免同一实体在一拍内生成多个互相冲突的移动 action。

### 5.3 服务端权威 tick 不追求极高频

逻辑 tick 仍然代表服务端权威节奏拍或世界步进。

```text
LogicTick N:
  Drain beatTick == N 的输入
  每个实体最多一个输入
  输入转 WorldAction
  执行规则
  生成 WorldDelta
```

不要用 20ms 逻辑 tick 解决手感问题。  
大世界工厂的服务端 tick 应优先稳定、可验证、可扩展。节奏输入的即时感应主要由客户端表现层和输入确认解决。

### 5.4 网络层拆分输入确认和结算结果

当前 `C2G_MoveRequest` 把输入提交和移动结算绑在一起：

```text
提交输入 -> 等服务端 tick 结算 -> 回包
```

更适合后续节奏输入的是：

```text
提交输入 -> 返回是否已缓存以及目标拍
目标拍结算后 -> 服务端通过 WorldDelta 广播最终结果
```

这可以拆成两个语义：

```text
InputAck
MoveResolved / WorldDelta
```

但这属于阶段 2，不应该混进阶段 1。阶段 1 可以先保持现有 RPC 行为，只在服务端内部把输入按拍合并。

### 5.5 客户端即时反馈优先于真实坐标预测

客户端按键后应立即反馈：

- 节拍命中反馈
- 方向反馈
- 目标格高亮
- 起步动画
- 输入已缓存提示

第一阶段不建议立即改客户端权威坐标。  
后续可以只预测表现，再逐步引入玩家局部坐标预测。

预测边界：

- 可以预测本地玩家短期表现。
- 可以预测目标格高亮和动作预备。
- 可以在低风险场景预测落格。
- 不要预测工厂机器主状态。
- 不要让 `ClientMapWorld` 直接裁决服务端规则。

### 5.6 服务端结果回来后软校正

客户端收到权威 `WorldDelta` 后：

- 如果预测一致，确认表现。
- 如果预测不一致，平滑过渡到服务端结果。
- 如果本地只做表现预测，则取消或修正表现即可。
- 多人最终状态仍以服务端 `WorldDelta` 为准。

推荐目标是：

```text
本地按键立即有反馈
服务端最终结果统一
预测错误可以被看起来不突兀地修正
```

## 6. 与 Minecraft 式大世界的关系

更贴近本项目的参考不是完整 rollback 对战，而是 Minecraft 式服务端权威大世界：

- 服务端掌握世界真相。
- 客户端可以先做本地表现。
- 服务端周期性同步最终状态。
- 客户端根据服务端结果校正。
- 大世界状态不因为单个玩家输入整体倒带。

`DG` 的工厂和机关系统也应该沿着这个思路走：

- 机器和工厂链由服务端 tick 推进。
- 区块状态由服务端管理。
- 玩家输入进入服务端 action / intent / tick / commit 边界。
- 客户端只负责显示、反馈和短期预测。
- 多人通过同一份权威 `WorldDelta` 收敛。

节奏输入只是改善玩家操作手感，不应该改变大世界权威模型。

## 7. 分阶段落地建议

### 阶段 1：节拍输入层

目标：解决“一拍多个输入”和“输入语义不是节拍意图”的问题。

任务：

- 新增 `BeatInputBuffer`。
- 内部使用 `entityId + beatTick` 作为 key。
- 同一实体同一拍只保留一个最终输入。
- 默认最后输入覆盖旧输入。
- 被替换输入立即完成为 `Replaced`。
- TickRunner 只消费当前 beat 的输入。
- 保持现有服务端权威结算。
- 暂时保持 `BroadcastDelta` 跟随逻辑 tick。
- 暂时不改客户端预测。
- 暂时不改完整 RPC 语义。

验证：

- Unity TestFramework 测试同实体同拍多输入只保留最后一个。
- Unity TestFramework 测试不同实体输入互不覆盖。
- Unity TestFramework 测试被替换输入不会一直等待。
- Unity TestFramework 测试当前拍 Drain 后不会重复消费。
- Unity TestFramework 测试未来拍输入不会提前消费。
- 手动验证一拍内快速按多个方向，只结算最后方向。

### 阶段 2：输入确认与即时反馈

目标：按键后立即有反馈，不等移动结算。

任务：

- 拆分输入确认和移动结算语义。
- 服务端收到合法输入后返回 `InputAck`。
- `InputAck` 明确输入被缓存到哪一拍。
- 客户端按键后立即显示方向或目标格反馈。
- 服务端仍在拍点统一结算。
- 最终坐标仍通过 `WorldDelta` 同步。

验证：

- Unity TestFramework 测试输入 ack 不依赖逻辑 tick 结算。
- Unity TestFramework 测试非法输入返回明确拒绝状态。
- 手动验证按键后立即出现目标格或方向反馈。
- 手动验证到拍点后才应用服务端最终落格或校正。

### 阶段 3：玩家局部表现预测

目标：让本地玩家操作更接近单机手感。

任务：

- 客户端记录 `clientInputId -> predicted presentation`。
- 客户端可以预测高亮、动画、预备移动。
- 低风险场景可以预测玩家落格表现。
- 服务端 `WorldDelta` 回来后对比预测。
- 一致则确认，不一致则软校正。
- 工厂机器和大世界主状态不参与客户端预测裁决。

验证：

- Unity TestFramework 测试同输入同初始状态下客户端轻量预测和服务端结果一致。
- Unity TestFramework 测试预测不一致时可以生成校正指令。
- 手动验证单人低延迟下无明显等待感。
- 手动验证阻挡、推箱、机关触发时客户端不会长期偏离。

### 阶段 4：局部冲突处理和小范围重算

目标：处理少量强交互场景，不回滚整个世界。

适用场景：

- 多人同拍抢同一格。
- 同拍互推。
- 同拍攻击打断。
- 小范围机关触发冲突。

任务：

- 为单个交互簇保留短窗口输入记录。
- 服务端在当前 tick 内稳定排序和裁决冲突。
- 必要时对局部 action 结果重算。
- 客户端只做表现修正。
- 不保存全世界每拍快照。
- 不回滚工厂生产主状态。

验证：

- Unity TestFramework 测试多人同拍抢格结果确定。
- Unity TestFramework 测试同拍互推结果确定。
- Unity TestFramework 测试同一输入集合在不同提交顺序下结果稳定。
- 手动双客户端验证网络抖动下双方最终状态一致。

### 阶段 5：特殊玩法再评估局部快照

目标：仅当未来出现明确强对抗玩法时，再考虑更重的局部快照方案。

暂不默认实施：

- 完整 rollback/replay。
- 全世界历史快照。
- 远端输入大范围预测。
- 工厂链历史倒带。
- 大规模 PVP 同步帧。

如果未来确实需要，应重新走 OpenSpec，单独评估：

- 快照范围。
- 最大历史窗口。
- 哪些系统可重放。
- 哪些系统不可回滚。
- 内存和 CPU 成本。
- 手动端到端验证方式。

## 8. 当前最推荐的下一步

下一步建议创建 OpenSpec 变更：

```text
add-rhythm-beat-input-buffer
```

这个变更应只覆盖阶段 1。不要把预测、`InputAck`、局部重算和 rollback 一起塞进去。

最小需求：

- 服务端输入按 `entityId + beatTick` 合并。
- 同一实体同一拍最多一个输入。
- 默认最后输入覆盖旧输入。
- 被覆盖输入有明确状态。
- TickRunner 只消费当前拍输入。
- 未来拍输入不会提前消费。
- 保留现有服务端权威结算。
- 保留现有 `WorldDelta` 广播模型。
- 添加 Unity TestFramework 覆盖输入合并、替换、消费边界。
- 明确手动端到端验证方式。

暂时不做：

- 20ms 逻辑 tick。
- 完整 rollback。
- 全世界快照。
- 客户端工厂状态预测。
- PVP 强对抗。
- 大规模服务器架构。
- 商城或账号系统。

## 9. 风险与取舍

### 风险 1：把节奏手感误解成高频服务端 tick

缓解：

- 服务端 tick 优先稳定。
- 客户端先做即时表现反馈。
- 输入确认和最终结算拆开。
- 不用 20ms tick 解决所有问题。

### 风险 2：客户端预测越界

缓解：

- 第一阶段不预测真实坐标。
- 后续只预测本地玩家和表现层。
- 工厂机器和世界主状态仍由服务端推进。
- `ClientMapWorld` 不直接裁决权威规则。

### 风险 3：一开始就设计过重

缓解：

- 第一阶段只做 `BeatInputBuffer`。
- `InputAck` 放阶段 2。
- 玩家预测放阶段 3。
- 局部冲突重算放阶段 4。
- 完整 rollback 默认不做。

### 风险 4：规则不确定性影响预测和重算

缓解：

- 规则层不依赖非确定性时间。
- 输入和 action 执行顺序稳定排序。
- 随机数使用可重放 seed。
- 关键规则添加一致性测试。

### 风险 5：多人最终状态不一致

缓解：

- 服务端 `GameWorld` 继续作为真相源。
- 所有最终坐标通过 `WorldDelta` 收敛。
- 手动验证必须包含双客户端同步。
- 自动测试覆盖同拍冲突和输入合并。

## 10. 推荐验证清单

自动测试只用 Unity 自带 TestFramework。

阶段 1 建议测试：

- 同一实体同一拍多输入只保留最终输入。
- 不同实体同一拍输入互不影响。
- 被替换输入返回明确状态。
- 当前拍 Drain 后不会重复消费。
- 未来拍输入不会提前消费。
- 过期输入按规则拒绝或进入指定后续拍。
- 服务端 `WorldDelta.ServerTick` 与结算拍一致。

阶段 2 建议测试：

- 合法输入 ack 不依赖逻辑 tick 结算。
- 非法输入 ack 返回拒绝状态。
- ack 的目标拍和服务端缓冲一致。
- 最终移动结果仍由服务端 `WorldDelta` 表达。

阶段 3 建议测试：

- 同输入同初始状态下预测结果和服务端结果一致。
- 预测失败时客户端能生成软校正。
- 客户端预测不会修改工厂主状态。

手动端到端验证：

- 启动服务端和一个客户端。
- 在一拍内快速按多个方向。
- 观察客户端即时反馈是否立刻出现。
- 观察到拍点时只结算最后方向。
- 启动两个客户端。
- 两个玩家同拍输入，观察双方最终状态一致。
- 模拟网络延迟后确认不会永久不同步。
- 验证工厂或机关状态仍以服务端结果为准。

不要执行 Unity Player build。

## 11. 最终建议

`DG` 可以做重手感节奏输入，但它的网络模型应继续站在大世界工厂这一边：

```text
大世界：服务端权威 tick
玩家手感：客户端即时反馈
玩家位置：局部预测和软校正
工厂机器：服务端确定性推进
多人冲突：服务端统一裁决
最终同步：WorldDelta 收敛
```

推荐路线：

```text
阶段 1：Beat Input Buffer
阶段 2：InputAck + 本地即时反馈
阶段 3：玩家局部表现预测 + 服务端软校正
```
