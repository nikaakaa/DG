# DG 策划案第二版：格子机关与状态驱动逻辑

## 一句话定位

DG 是一个以格子移动、机关地格、可推动实体、自动实体和多人协作为核心的规则驱动游戏。

玩家每次输入不是直接把所有结果一次性算完，而是向权威世界提交一次行动。行动会创建或改变世界状态，世界再通过固定的逻辑 tick 逐步推进这些状态。这样可以支持推箱子、传送带、自动球、按钮、门、连锁机关，也能保证多人环境下结果确定。

## 核心体验

玩家在格子地图上行动。地图不是静态棋盘，而是由各种可组合规则构成的机关场。

一个玩家行动可能会产生：

```text
玩家尝试向右移动
  -> 前方有箱子
  -> 创建一次向右推的状态
  -> 后续逻辑 tick 逐步检查和推进推力
  -> 如果前方最终有空位，相关实体按规则移动
  -> 如果中途被其他玩家或机关改变，后续 tick 按新状态重新判定
```

游戏乐趣来自：

- 预判自己行动后世界会如何变化
- 利用传送带、箱子、球、阻挡体、按钮、门改变局面
- 多名玩家在同一个权威世界里互相影响
- 自动实体和机关持续制造压力或机会
- 调试建造工具可以快速摆放、拖拽、删除并验证规则组合

## 世界基础规则

### 世界是格子化的

地图由格子组成，实体占据格子或地格。

第一版默认：

```text
1 Unity unit = 1 格
1 entity 主要位于 1 个格子
```

### 实体由功能组成

实体不靠“种类”决定全部行为，而是由功能组件组合出规则。

例如：

```text
玩家：
  有位置
  可移动
  可阻挡
  可推动
  可由玩家控制

箱子：
  有位置
  可阻挡
  可推动

传送带：
  有位置
  有方向
  可被进入
  进入后尝试推动实体

球：
  有位置
  有方向
  可移动
  可阻挡
  可推动
  可反弹
  可自动行动
```

这样未来可以组合出新机关，而不是为每一种物体写一套完全独立规则。

## Tick 划分

DG 需要明确区分几种 tick。它们不是同一个东西。

### Server Loop Tick

服务器轮询 tick。

职责：

```text
收包
处理网络会话
推进计时器
把到期任务放入队列
触发 Logic Tick
触发 Network Flush
```

它可以比较高频，但不应该直接代表玩法节奏。

### Logic Tick

权威世界逻辑 tick。

这是唯一推进玩法规则的节奏。所有格子移动、推力传播、自动实体、机关状态，都在 Logic Tick 内按确定顺序推进。

每个 Logic Tick 做：

```text
1. 取出已接受的玩家行动和调试行动
2. 把行动转成世界状态变化或持续状态
3. 推进已有持续状态
4. 按固定顺序提交本 tick 的合法结果
5. 标记 dirty state
```

Logic Tick 可以是固定间隔，例如：

```text
LogicTickIntervalMs = 100
```

这个值决定世界规则推进速度，不等于玩家输入冷却，也不等于客户端动画帧率。

### Action Step

行动步。

玩家输入、调试建造、自动实体到期行动，都会先变成 Action。

Action 的职责不是一次性算完整个连锁，而是：

```text
验证行动是否合法
创建或修改世界状态
必要时创建持续状态
```

例如：

```text
PlayerMoveAction
PlayerPushAction
DebugPlaceEntityAction
DebugDeleteEntityAction
AutoMoveAction
```

玩家行动可以有自己的冷却：

```text
PlayerActionCooldownMs = 100~200
```

这表示玩家多久可以提交一次行动，不表示世界多久才推进一次。

### Network Flush Tick

网络同步 tick。

职责：

```text
收集已经提交的 dirty state
生成 delta
广播给客户端
```

Network Flush 可以和 Logic Tick 同频，也可以更低频或合批。它不负责决定玩法结果。

第一版可以简单处理：

```text
每个 Logic Tick 结束后 flush 一次
```

后续如果需要优化，再把 flush 频率和 Logic Tick 拆开。

### Client Render Tick

客户端渲染 tick。

职责：

```text
播放动画
插值
显示预测
显示调试 UI
接收服务器 delta 并校正表现
```

客户端帧率不改变权威世界规则。

## 状态模型

### 已提交状态

已提交状态是当前权威世界真实状态。

例如：

```text
实体当前位置
实体方向
格子占用
门是否打开
按钮是否按下
```

所有碰撞、阻挡、同步、后续规则判定，都默认读取已提交状态。

### 持续状态

持续状态是还在推进中的规则过程。

例如：

```text
PushPropagation
MovingState
AutoMoveState
MechanismState
```

持续状态每个 Logic Tick 都会重新读取当前已提交状态，再决定下一步是否合法。

这点很重要：

```text
如果一个推箱子连锁还没有推进到最后一个箱子
那么最后一个箱子在权威世界里仍然没有被推动
其他玩家或机关仍然可以改变它
后续 Logic Tick 会基于改变后的世界重新判定
```

这让规则更接近“世界正在运转”，而不是“玩家一次输入冻结全世界并离线算完”。

## 推箱子规则

### 基础推

玩家尝试移动到被可推动实体占据的格子时，不是直接失败，而是尝试创建推力状态。

```text
玩家向右行动
  -> 右侧是可推动箱子
  -> 创建 PushPropagation(direction = Right)
```

### 推力传播

推力不是必须在一次 Action Step 内算完。

推荐第一版规则：

```text
每个 Logic Tick 推进一次 PushPropagation
每次推进只处理当前推力前沿附近的一个确定步骤
每一步都重新检查当前格子占用
只有本 tick 成功提交的实体才真正改变坐标
```

如果前方为空：

```text
提交一个移动结果
推力状态完成或进入回传提交阶段
```

如果前方是可推动实体：

```text
推力继续向前传播
暂时不移动尚未被提交的实体
```

如果前方是不可推动阻挡：

```text
推力失败
未提交的实体保持原状
```

### 为什么不把整条链一次性算完

如果一次玩家输入直接把整条链算完，会出现几个问题：

```text
长链机关可能一次 tick 计算太多
其他玩家无法介入正在传播的过程
动画表现和规则状态容易脱节
循环机关需要人为截断
```

改成持续状态后，世界每个 Logic Tick 都只推进确定的一小步，玩家可以看见过程，也可以在过程还没影响到某个实体前改变它。

## 自动实体规则

自动实体不是依赖玩家输入才运行，而是自己拥有节奏状态。

例如：

```text
AutoMoveIntervalTicks = 3
```

每个 Logic Tick：

```text
自动实体累计或检查自己的计时
到期后创建 AutoMoveAction
AutoMoveAction 再按普通行动规则进入世界
```

自动实体和玩家行动使用同一套 Action + State 推进模型。

例如自动球：

```text
球到期向当前方向移动
  -> 前方为空，提交移动
  -> 前方阻挡，提交反弹方向
  -> 前方可推动，创建推力状态
```

## 机关地格规则

### 传送带

传送带是第一种核心机关地格。

规则：

```text
实体进入传送带所在格
  -> 如果实体可被移动
  -> 创建或更新一个由传送带产生的推动状态
```

传送带本身不阻挡实体进入。

第一版传送带不需要每帧全图扫描，而是优先使用事件或状态：

```text
实体本 tick 进入某格
  -> 查询该格地格能力
  -> 如果是传送带，创建推动状态
```

如果一个实体一直站在传送带上，是否每个 Logic Tick 都被推动，需要作为传送带能力配置：

```text
OnEnterOnly
EveryLogicTickWhileOccupied
IntervalWhileOccupied
```

第一版推荐先做：

```text
EveryLogicTickWhileOccupied
```

这样传送带更直观，也更方便验证自动推进。

### 阻挡体

阻挡体占据格子并阻止其他阻挡实体进入。

```text
实体尝试进入阻挡格
  -> 如果不能推动或推力失败
  -> 移动失败
```

### 反弹物体

反弹物体在撞到阻挡体、玩家或指定实体时改变方向。

```text
球向右移动
右侧被阻挡
  -> 球不移动
  -> 方向变为左
```

## 确定性规则

DG 不应该把“最多处理 32 个 trigger”当成正常玩法规则。

正常玩法规则应该靠状态和 tick 自然推进：

```text
每个 Logic Tick 固定处理顺序
每个状态只推进定义好的一个步骤
每一步都重新验证当前世界
所有提交结果都按确定顺序写入
```

如果同一个 tick 内多个行动冲突，需要明确排序：

```text
1. 服务器接受行动的 tick
2. 行动类型优先级
3. 玩家或实体 id
4. action id
```

第一版可以简单规定：

```text
同一 Logic Tick 内，按 action id 升序处理
同一实体同 tick 只允许一个最终位移提交成功
后处理的冲突行动失败或保持 pending
```

### 安全上限只做开发保护

可以保留内部保护，例如：

```text
单个 Logic Tick 最大状态推进数量
单个状态最大存活 tick
单个实体最大 pending 状态数
```

但这些不是正常玩法的一部分。

如果触发保护，说明：

```text
地图配置有问题
状态机有 bug
规则缺少终止条件
```

第一版应记录错误并在调试 UI 中显示，而不是把它设计成玩家可利用的规则。

## 多人规则

所有玩家处于同一个服务器权威世界。

玩家之间可以互相影响：

```text
玩家 A 正在推动一条箱子链
推力还没有传播到最后一个箱子
玩家 B 在下一个行动里移动了最后一个箱子
后续推力传播会基于新状态重新判定
```

多人同步目标：

```text
每个客户端最终看到的已提交世界状态一致
客户端可以提前播放动画
但权威结果以服务器提交状态为准
```

## 调试建造玩法

短期内调试工具用于快速验证规则。

调试工具支持：

```text
建造阻挡体
建造箱子
建造球
建造传送带
旋转传送带方向
拖拽实体
删除实体
查看 pending state
查看 dirty state
查看当前 Logic Tick
暂停或单步推进 Logic Tick
```

这些功能第一版是开发调试工具。后续如果玩法成立，可以演化成正式建造玩法。

## 服务端权威原则

服务端是唯一权威。

客户端可以：

```text
显示预测
显示目标格
播放移动动画
显示机关反应预览
显示 pending 状态调试信息
```

但最终结果以服务器为准。

如果客户端预测和服务器结果不同：

```text
客户端校正到服务器已提交状态
```

## 第一版 Demo 应该证明什么

第一版玩法 Demo 不追求内容多，而是证明规则模型成立。

需要证明：

```text
玩家能移动
玩家会被阻挡体阻挡
玩家能推动箱子
箱子推力可以跨 Logic Tick 传播
未被推力传播到的箱子仍可被其他行动改变
传送带能持续推动站在上面的实体
球能自动行动并反弹
两个客户端看到同一个已提交结果
调试工具能摆放、删除、拖拽并单步查看逻辑状态
```

## 下一步开发重点

推荐先做玩法规则底座，而不是先做完整预测。

顺序：

```text
1. 明确拆分 Server Loop Tick、Logic Tick、Network Flush Tick
2. 把玩家输入改成 Action Queue
3. 增加持续状态容器，例如 PushPropagation、MovingState
4. 实现推箱子的跨 Logic Tick 传播
5. 让传送带按 EveryLogicTickWhileOccupied 创建推动状态
6. 把自动球改成按自身 interval 创建 AutoMoveAction
7. 给调试 UI 增加 pending state、tick、单步推进显示
8. 再做可见同步、客户端镜像生命周期
9. 最后做客户端预测、校正、插值
```
